# 0.20.0 - Archivado reversible confirmado / Confirmed reversible archiving

Fecha / Date: 2026-08-08

## Español

### Objetivo

Completar la primera acción real del flujo operativo. Una candidata de retención
debe poder revisarse, previsualizarse, archivarse de forma deliberada y
restaurarse sin salir del dashboard.

### Resultado

- `Revisar y archivar` localiza la fila exacta y abre su ficha operativa.
- `Preparar archivado` consulta el plan sin modificar el JSONL ni exponer su
  ruta local.
- La confirmación es un segundo paso y la API solo acepta el literal `ARCHIVE`.
- La API vuelve a comprobar la política justo antes de mover el archivo. Una
  sesión que dejó de ser candidata recibe un conflicto y no se archiva.
- Cada registro expone una clave SHA-256 opaca derivada de su identidad completa;
  así no se actúa sobre otra copia que comparta el mismo identificador.
- El archivo movido conserva junto a él un recibo `.restore.json` con los datos
  mínimos necesarios para devolverlo a su ubicación original.
- La cola `Archivadas recuperables` descubre esos recibos tras una recarga o
  reinicio y permite restaurar la sesión.
- Tras restaurar, Codex se vuelve a escanear y la sesión reaparece en el
  inventario y en su ficha.

### Contrato y seguridad

- La acción web se limita a archivos JSONL directos de Codex con estado `active`
  que sigan superando `archive_after_days`.
- Los ZIP de ChatGPT, sus entradas compartidas y el registro de Claude Code no
  se mueven desde el dashboard.
- Las respuestas muestran nombres de archivo, tamaño y umbral, nunca la ruta
  fuente ni `archive_dir`.
- Si el destino ya existe, el origen falta o la ubicación original está ocupada,
  la operación se detiene con conflicto.
- Compose crea una política inicial persistente con `archive_dir =
  "/data/archive"`. El montaje Codex permite escritura para esta acción; Claude
  Code permanece como solo lectura y el único puerto publicado sigue ligado a
  `127.0.0.1`.
- El archivado CLI existente mantiene su contrato: simulación salvo `--apply`.
  Solo el flujo reversible del dashboard crea recibos de recuperación.

### Verificación

- 19 pruebas Python superadas, incluidas previsualización, confirmación inválida,
  movimiento, recibo persistente y restauración.
- 6 pruebas Angular superadas, incluido el flujo completo desde la cola y la
  recuperación después de cerrar la ficha.
- Build Angular de producción completado.
- `npm audit --audit-level=moderate`: 0 vulnerabilidades.
- Detector Impeccable sobre HTML, SCSS y TypeScript: 0 hallazgos.
- Stack Docker 0.20 construido con API saludable y dashboard disponible en
  `http://127.0.0.1:4200`.
- Navegador real validado únicamente con la previsualización no destructiva; no
  se archivó ninguna sesión real del usuario durante las comprobaciones.

### Límites conocidos

- La recuperación necesita que el recibo y el archivo archivado sigan presentes
  y que la ruta original esté libre.
- Borrar manualmente el recibo elimina la recuperación desde la interfaz, aunque
  el JSONL archivado continúe existiendo.
- Generar relevos y descartar falsos bloqueos desde la ficha siguen pendientes.

## English

### Goal

Complete the first real action in the operational flow. A retention candidate
must be reviewable, previewable, deliberately archived, and restorable without
leaving the dashboard.

### Result

- `Review and archive` locates the exact row and opens its operational record.
- `Prepare archive` fetches the plan without changing the JSONL or exposing its
  local path.
- Confirmation is a separate step, and the API accepts only the `ARCHIVE`
  literal.
- The API checks policy again immediately before moving the file. A session that
  is no longer eligible receives a conflict and is not archived.
- Each record exposes an opaque SHA-256 key derived from its complete identity,
  so an action cannot target another copy with the same session identifier.
- The moved file keeps a `.restore.json` receipt beside it with the minimum data
  required to return it to its original location.
- The `Recoverable archives` queue discovers those receipts after a page reload
  or restart and restores the session.
- After restoration, Codex is scanned again and the session returns to the
  inventory and its operational record.

### Contract and security

- The web action is limited to direct Codex JSONL files with `active` status that
  still exceed `archive_after_days`.
- ChatGPT ZIP files, their shared entries, and the Claude Code registry are not
  moved from the dashboard.
- Responses show file names, size, and threshold, never the source path or
  `archive_dir`.
- Existing destinations, missing sources, or occupied original locations stop
  the operation with a conflict.
- Compose creates an initial persistent policy with `archive_dir =
  "/data/archive"`. The Codex mount is writable for this action; Claude Code
  remains read-only, and the only published port stays bound to `127.0.0.1`.
- Existing CLI archiving keeps its contract: dry run unless `--apply` is passed.
  Only the dashboard's reversible flow creates recovery receipts.

### Verification

- 19 Python tests passed, including preview, invalid confirmation, move,
  persistent receipt, and restoration.
- 6 Angular tests passed, including the complete queue flow and recovery after
  closing the operational record.
- Production Angular build completed.
- `npm audit --audit-level=moderate`: 0 vulnerabilities.
- Impeccable detector over HTML, SCSS, and TypeScript: 0 findings.
- Docker 0.20 stack built with a healthy API and dashboard available at
  `http://127.0.0.1:4200`.
- Real-browser validation used only the non-destructive preview; no real user
  session was archived during verification.

### Known limits

- Recovery requires both the receipt and archived file to remain present and the
  original path to be free.
- Manually deleting the receipt removes recovery from the interface even when
  the archived JSONL still exists.
- Handoff generation and false-block dismissal from the record remain pending.
