# 0.17.0 - Dashboard operativo / Operational dashboard

## Español

### Objetivo

Corregir dos fallos de producto observados en el uso real: una actualización
parecía no funcionar mientras volvía a leer cientos de sesiones y las señales
de bloqueo quedaban ocultas debajo del inventario. El hito prioriza decisiones
operativas y deja la tabla completa como herramienta de consulta.

### Actualización incremental

`scan_codex` acepta los metadatos ya indexados. Para cada JSONL compara ruta
resuelta, estado (`active` o `archived`) y tamaño:

- si no han cambiado, reutiliza los metadatos guardados y actualiza el título
  desde `session_index.jsonl`;
- si el archivo es nuevo, cambia de tamaño o se mueve entre estados, vuelve a
  leerlo completo;
- si desaparece, la sincronización lo elimina del inventario Codex.

Codex produce JSONL anexables, por lo que el tamaño es la señal mínima suficiente
para evitar releer historiales grandes durante un refresco normal. Una reescritura
externa que conserve exactamente el tamaño no se detecta; ejecutar con una base
nueva fuerza un escaneo completo.

El contrato de `GET/POST /api/refresh` añade `updated`, `reused` y
`duration_seconds`. Estos campos distinguen una actualización sin cambios de una
operación detenida. La CLI `scan`, `maintain`, el arranque Compose y el botón web
usan el mismo camino incremental cuando ya existe una base.

### Cola de atención

La primera zona de trabajo después de las métricas es **Qué requiere atención**:

- posibles bloqueos, explicados como inicio detectado sin evento de cierre tras
  el umbral configurado;
- candidatas a archivo según la política de retención;
- nombre, última actividad y repositorio de cada señal;
- acción **Localizar**, que filtra el inventario por agente y estado, calcula la
  página correcta y desplaza la vista a la tabla.

La heurística de bloqueo no se amplía: continúa siendo deliberadamente
conservadora y solo considera sesiones Codex activas cuyo último evento terminal
es `task_started`. El cambio hace visible y comprensible la señal existente sin
inventar estados de proceso.

### Seguridad y alcance

- Las fuentes Codex y Claude Code siguen montadas como solo lectura en Compose.
- El refresco escribe únicamente metadatos normalizados en SQLite.
- La cola no aplica archivado ni modifica sesiones; `--apply` y
  `--apply-policy` siguen siendo explícitos en la CLI.
- Rutas de archivos y transcripciones continúan fuera de las respuestas API.

### Verificación

- 17 pruebas Python, incluida reutilización sin lectura y relectura al anexar un
  evento.
- 4 pruebas Angular para prioridad de la cola, explicación del bloqueo,
  localización con identificadores duplicados y métricas del refresco.
- Build Angular de producción y detector Impeccable sin hallazgos.
- Auditoría npm sin vulnerabilidades.
- Imágenes API y dashboard 0.17.0 construidas y stack Compose validado contra el
  inventario local real.
- Actualización repetida sobre 480 registros completada en 2,9 segundos: 1
  archivo cambiado y 479 metadatos reutilizados. La implementación anterior
  seguía ejecutándose después de 29 segundos en la misma comprobación.
- Revisión visual adaptable y consola del navegador sin errores.

### Límites conocidos

- La detección de bloqueos es una señal de revisión, no una prueba de que un
  proceso siga vivo o esté colgado.
- La cola localiza sesiones, pero todavía no archiva desde la web.
- La primera indexación completa sigue leyendo todos los archivos.
- Autenticación y acceso fuera de loopback permanecen fuera de alcance.

## English

### Goal

Fix two product failures found in real use: refresh appeared broken while it
read hundreds of sessions again, and blocked signals were hidden below the
inventory. This milestone prioritizes operational decisions and keeps the full
table as a lookup tool.

### Incremental refresh

`scan_codex` accepts previously indexed metadata. For each JSONL it compares
resolved path, status (`active` or `archived`), and size:

- unchanged files reuse stored metadata and refresh their title from
  `session_index.jsonl`;
- new files, size changes, or moves between states trigger a full reread;
- disappeared files are removed from the Codex inventory during synchronization.

Codex writes append-oriented JSONL, so file size is the smallest useful signal
for avoiding large history rereads during a normal refresh. An external rewrite
that preserves the exact size is not detected; using a new database forces a
full scan.

The `GET/POST /api/refresh` contract adds `updated`, `reused`, and
`duration_seconds`. These fields distinguish an unchanged refresh from a stalled
operation. CLI `scan`, `maintain`, Compose startup, and the web button share the
incremental path whenever a database already exists.

### Attention queue

The first working area after metrics is **What needs attention**:

- potentially blocked sessions, explained as a detected start without a closing
  event after the configured threshold;
- archive candidates selected by retention policy;
- name, latest activity, and repository for every signal;
- a **Locate** action that filters by agent and status, selects the correct page,
  and moves to the inventory table.

The blocked-session heuristic is not broadened. It remains deliberately
conservative and only considers active Codex sessions whose latest terminal
event is `task_started`. The change makes the existing signal visible and
understandable without inventing process state.

### Security and scope

- Codex and Claude Code sources remain read-only Compose mounts.
- Refresh writes normalized metadata to SQLite only.
- The queue does not archive or modify sessions; CLI `--apply` and
  `--apply-policy` remain explicit.
- Source paths and transcripts remain absent from API responses.

### Verification

- 17 Python tests, including no-read reuse and reread after appending an event.
- 4 Angular tests for queue priority, blocked-signal explanation, duplicate-ID
  location, and refresh metrics.
- Production Angular build and Impeccable detector with no findings.
- npm audit with zero vulnerabilities.
- API and dashboard 0.17.0 images built and Compose stack validated against the
  real local inventory.
- Repeated refresh over 480 records completed in 2.9 seconds: 1 changed file and
  479 reused metadata records. The previous implementation was still running
  after 29 seconds in the same check.
- Responsive visual review and browser console with no errors.

### Known limits

- Blocked detection is a review signal, not proof that a process is alive or
  hung.
- The queue locates sessions but does not yet archive from the web.
- The first full index still reads every file.
- Authentication and access beyond loopback remain out of scope.
