# 0.21.0 - Descarte reversible de falsos bloqueos / Reversible false-block dismissal

Fecha / Date: 2026-08-09

## Español

### Objetivo

Convertir la señal de posible bloqueo en una revisión operativa gestionable. El
usuario debe poder entender la heurística, descartar un falso positivo y
deshacer la decisión sin modificar la sesión original.

### Resultado

- `Revisar señal` localiza la fila exacta y abre su ficha operativa.
- La ficha explica que la detección depende de `task_started`, la ausencia de un
  cierre posterior y el umbral `blocked_after_hours`.
- `Marcar como no bloqueada` abre una confirmación separada; la API solo acepta
  el literal `NOT_BLOCKED`.
- El descarte se guarda en SQLite con la clave opaca del registro, su última
  actividad y la fecha de revisión.
- La cola distingue señales activas y descartadas. Una señal descartada puede
  reactivarse desde la cola o desde la ficha.
- El informe de bloqueos renderizado en la interfaz excluye los descartes
  vigentes, igual que la cola de atención.
- Una nueva `last_activity_at` invalida automáticamente el descarte anterior. Si
  la sesión vuelve a cumplir la heurística, reaparece para revisión.

### Contrato y seguridad

- Descartar no modifica, mueve ni archiva ningún JSONL.
- La API vuelve a comprobar la heurística antes de aceptar la decisión.
- La acción usa `record_key`, no el identificador potencialmente duplicado de la
  sesión.
- El historial almacenado contiene solo identificador, clave, marcas de tiempo y
  ninguna conversación ni ruta nueva.
- La restauración elimina únicamente la decisión local de descarte.

### Verificación

- 20 pruebas Python superadas, incluida persistencia, confirmación inválida,
  reactivación y caducidad automática tras nueva actividad.
- 7 pruebas Angular superadas, incluido el flujo completo de descarte y
  restauración desde la ficha.
- Build Angular de producción completado.
- `npm audit --audit-level=moderate`: 0 vulnerabilidades.
- Detector Impeccable sobre HTML, SCSS y TypeScript: 0 hallazgos.
- Stack Docker 0.21 construido con API saludable y dashboard disponible en
  `http://127.0.0.1:4200`.
- La validación sobre los datos reales fue de solo lectura; no se descartó ni
  reactivó ninguna señal real del usuario.

### Límites conocidos

- El descarte solo gobierna la cola y el informe servidos por la API. El comando
  CLI `blocked` sigue mostrando la detección bruta.
- No se solicita una justificación de texto libre; el hito registra únicamente
  la decisión explícita para evitar almacenar contenido innecesario.
- La generación de relevo desde la ficha operativa permanece pendiente.

## English

### Goal

Turn the potentially blocked signal into a manageable operational review. The
user must be able to understand the heuristic, dismiss a false positive, and
undo that decision without changing the original session.

### Result

- `Review signal` locates the exact row and opens its operational record.
- The record explains that detection depends on `task_started`, no later closing
  event, and the `blocked_after_hours` threshold.
- `Mark as not blocked` opens a separate confirmation; the API accepts only the
  `NOT_BLOCKED` literal.
- SQLite stores the dismissal with the opaque record key, last activity, and
  review timestamp.
- The queue separates active and dismissed signals. A dismissed signal can be
  restored from either the queue or its record.
- The blocked report rendered in the interface excludes active dismissals just
  like the attention queue.
- A new `last_activity_at` automatically invalidates the previous dismissal. If
  the session matches the heuristic again, it returns for review.

### Contract and safety

- Dismissing never changes, moves, or archives a JSONL file.
- The API checks the heuristic again before accepting the decision.
- The action uses `record_key`, not a potentially duplicated session identifier.
- Stored history contains only an identifier, key, and timestamps; it adds no
  conversation content or new path.
- Restoration removes only the local dismissal decision.

### Verification

- 20 Python tests passed, including persistence, invalid confirmation,
  restoration, and automatic expiry after new activity.
- 7 Angular tests passed, including the complete dismissal and restoration flow
  from the operational record.
- Production Angular build completed.
- `npm audit --audit-level=moderate`: 0 vulnerabilities.
- Impeccable detector over HTML, SCSS, and TypeScript: 0 findings.
- Docker 0.21 stack built with a healthy API and dashboard available at
  `http://127.0.0.1:4200`.
- Validation against real data was read-only; no real user signal was dismissed
  or restored.

### Known limits

- Dismissal governs only the queue and report served by the API. The `blocked`
  CLI command continues to show raw detection.
- No free-form rationale is requested; the milestone records only the explicit
  decision to avoid storing unnecessary content.
- Handoff generation from the operational record remains pending.
