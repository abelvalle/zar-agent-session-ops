# 0.10.0 - Stack Docker local / Local Docker stack

## Español

### Objetivo

Ejecutar la API y el dashboard con un único comando reproducible, preservando
el modelo de seguridad local y sin convertir el proyecto en un servicio
público.

### Implementación

- `compose.yaml` coordina `api` y `dashboard` en la red privada predeterminada.
- La API usa `python:3.13.11-slim-trixie`, instala el paquete y se ejecuta como
  el usuario no privilegiado `app` con UID/GID 10001.
- El dashboard se compila con `node:26.5.0-alpine3.24` y Nginx
  `1.31.2-alpine` sirve los archivos estáticos en el puerto interno 8080.
- Las tres bases están fijadas por etiqueta exacta y digest multi-arquitectura.
- Nginx resuelve `api` por el DNS de Compose y reenvía `/api/**` al puerto
  interno 8000; la API no publica ningún puerto al host.
- El dashboard publica exclusivamente
  `127.0.0.1:${ZAR_DASHBOARD_PORT:-4200}`.
- `${CODEX_HOME}` se monta en `/codex` como solo lectura. La API realiza un
  escaneo inicial y después inicia Uvicorn.
- La base SQLite y `config.toml` viven en el volumen nombrado `session-data`.
  `docker compose down` elimina contenedores y red, pero conserva ese volumen.
- El healthcheck usa `urllib` de la biblioteca estándar y concede cinco minutos
  al escaneo inicial antes de contar fallos.

### Seguridad y operación

- El contenedor de la API no se ejecuta como root y no puede escribir en el
  origen Codex.
- El único punto de entrada del host es Nginx en loopback. La API permanece
  accesible solo para servicios de la red de Compose.
- `GITHUB_TOKEN` es opcional y no se persiste en SQLite. Como cualquier variable
  de entorno de un contenedor, puede ser inspeccionada por administradores del
  Docker local.
- El stack sigue sin autenticación y no es apto para exposición pública.

### Verificación

- Docker Desktop 29.6.2 y Compose 5.3.1 validaron la configuración.
- Las imágenes `zar-agent-session-ops-api:0.10.0` y
  `zar-agent-session-ops-dashboard:0.10.0` se construyeron desde cero.
- Un arranque limpio conservando el volumen completó el escaneo de 461 sesiones
  y puso ambos servicios en marcha en 153,1 segundos.
- `GET http://127.0.0.1:4200/api/health` devolvió `ok` y versión `0.10.0`;
  el inventario devolvió 461 sesiones.
- El dashboard respondió 200 y renderizó 58 sesiones activas, 403 archivadas,
  una posible bloqueada y paginación funcional. La acción `Actualizar` se
  comprobó en navegador.
- La API se ejecutó como UID 10001; `/codex` apareció como bind de solo lectura
  y `/data` como volumen de escritura.
- El host publicó `127.0.0.1:4200 -> 8080`; no existió publicación del puerto
  8000 de la API.
- 11 pruebas Python y 2 pruebas Angular aprobadas; `npm audit` no encontró
  vulnerabilidades.

### Límites conocidos

- El escaneo ocurre al iniciar la API. El botón `Actualizar` vuelve a leer la
  base, pero no inicia un nuevo escaneo de archivos.
- Los bind mounts de Docker Desktop pueden hacer que el primer arranque tarde
  varios minutos con inventarios grandes.
- Las imágenes se construyen localmente; este hito no publica un registro ni
  incorpora despliegue remoto.
- No se añaden autenticación, TLS ni acceso fuera de loopback.

## English

### Goal

Run the API and dashboard with one reproducible command while preserving the
local security model and without turning the project into a public service.

### Implementation

- `compose.yaml` coordinates `api` and `dashboard` on the default private
  network.
- The API uses `python:3.13.11-slim-trixie`, installs the package, and runs as
  the unprivileged `app` user with UID/GID 10001.
- The dashboard builds under `node:26.5.0-alpine3.24`; Nginx
  `1.31.2-alpine` serves the static output on internal port 8080.
- All three bases are pinned by exact tag and multi-architecture digest.
- Nginx resolves `api` through Compose DNS and proxies `/api/**` to internal
  port 8000; the API publishes no host port.
- The dashboard publishes only
  `127.0.0.1:${ZAR_DASHBOARD_PORT:-4200}`.
- `${CODEX_HOME}` is mounted read-only at `/codex`. The API performs an initial
  scan and then starts Uvicorn.
- SQLite and `config.toml` live in the named `session-data` volume.
  `docker compose down` removes containers and the network but preserves it.
- The healthcheck uses standard-library `urllib` and allows five minutes for
  the initial scan before failures count.

### Security and operation

- The API container does not run as root and cannot write to the Codex source.
- The only host entry point is Nginx on loopback. The API remains reachable only
  by services on the Compose network.
- `GITHUB_TOKEN` is optional and is not persisted in SQLite. Like any container
  environment variable, local Docker administrators can inspect it.
- The stack still has no authentication and is unsuitable for public exposure.

### Verification

- Docker Desktop 29.6.2 and Compose 5.3.1 validated the configuration.
- `zar-agent-session-ops-api:0.10.0` and
  `zar-agent-session-ops-dashboard:0.10.0` were built from scratch.
- A clean start that retained the volume scanned 461 sessions and started both
  services in 153.1 seconds.
- `GET http://127.0.0.1:4200/api/health` returned `ok` and version `0.10.0`;
  the inventory returned 461 sessions.
- The dashboard returned 200 and rendered 58 active sessions, 403 archived
  sessions, one potentially blocked session, and working pagination. The
  `Refresh` action was exercised in a browser.
- The API ran as UID 10001; `/codex` was a read-only bind and `/data` a writable
  volume.
- The host published `127.0.0.1:4200 -> 8080`; API port 8000 had no host
  publication.
- 11 Python and 2 Angular tests passed; `npm audit` found no vulnerabilities.

### Known limits

- Scanning happens at API startup. The `Refresh` button reloads the database but
  does not start a new file scan.
- Docker Desktop bind mounts can make the first start take several minutes for
  large inventories.
- Images are built locally; this milestone adds neither registry publication
  nor remote deployment.
- Authentication, TLS, and access beyond loopback remain out of scope.
