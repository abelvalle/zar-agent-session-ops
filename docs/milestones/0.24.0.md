# 0.24.0 - Límite local vigente de Codex / Live local Codex limit

Fecha / Date: 2026-08-10

## Español

### Problema comprobado

El dashboard mostraba 54% disponible mientras Codex mostraba 4%. Ambos valores
procedían de la misma ventana semanal, pero la interfaz estaba leyendo una
instantánea de SQLite observada el 2026-08-09. El JSONL de la tarea activa ya
contenía una observación posterior con 96% consumido y el mismo reinicio.

### Resultado

- `GET /api/usage` busca el JSONL Codex modificado más recientemente y recorre
  sus eventos desde el final hasta encontrar un `token_count` con límite válido.
- Si un archivo reciente no contiene telemetría, continúa con el siguiente sin
  reindexar ni reescribir las 488 sesiones del inventario.
- La respuesta incluye porcentaje consumido, ventana, reinicio, hora observada,
  antigüedad y estado `stale`; nunca incluye la ruta del JSONL.
- El dashboard usa este endpoint solo para el límite vigente. El total procesado
  continúa siendo el histórico deduplicado de las sesiones indexadas.
- La hora de la última lectura es visible. Tras 15 minutos sin una observación
  nueva aparece `Dato obsoleto` con una acción de recuperación concreta.
- `Actualizar` solicita primero la telemetría ligera y mantiene después el
  refresco incremental completo con su duración y registros cambiados.

### Contrato y privacidad

`GET /api/usage` es de solo lectura, no persiste datos y no devuelve rutas,
transcripciones ni contenido de mensajes. El porcentaje representa la última
observación emitida localmente por Codex; no se presenta como una consulta
autenticada a la cuenta ni como una equivalencia fija en tokens.

La [documentación oficial de Codex](https://learn.chatgpt.com/docs/pricing)
indica que los límites vigentes se consultan en el panel de uso o mediante
`/status`, que las tareas pueden consumir cantidades distintas según modelo,
contexto, razonamiento y herramientas, y que pueden existir límites semanales.

### Verificación

- 24 pruebas Python superadas, incluidas selección del último evento válido,
  fuente ausente, respuesta API, obsolescencia y ausencia de rutas.
- 7 pruebas Angular superadas con 4% disponible, 96% consumido, hora observada,
  aviso de obsolescencia y doble fase de actualización.
- Build Angular de producción completado dentro del presupuesto.
- `npm audit --audit-level=moderate`: 0 vulnerabilidades.
- Detector Impeccable sobre HTML, SCSS y TypeScript: 0 hallazgos.
- Stack Docker 0.24 construido con API saludable y dashboard disponible en
  `http://127.0.0.1:4200`.
- Navegador real validado contra la fuente local activa: mostró 2% disponible y
  98% consumido desde una observación de menos de un minuto, sin modificar
  sesiones ni decisiones de ciclo de vida.

### Límite conocido

Codex no expone aquí una API oficial de cuenta. Si no emite eventos locales, el
último valor puede envejecer; la interfaz lo hace explícito en vez de mostrarlo
como actual.

## English

### Verified problem

The dashboard showed 54% available while Codex showed 4%. Both values belonged
to the same weekly window, but the UI was reading a SQLite snapshot observed on
2026-08-09. The active task JSONL already contained a later observation with
96% consumed and the same reset time.

### Result

- `GET /api/usage` finds the most recently modified Codex JSONL and walks its
  events backwards until it finds a `token_count` with a valid limit.
- When a recent file has no telemetry, it continues to the next one without
  reindexing or rewriting all 488 inventory records.
- The response includes consumed percentage, window, reset, observation time,
  age, and `stale` state; it never includes the JSONL path.
- The dashboard uses this endpoint only for the current limit. Total processed
  tokens remain the deduplicated history from indexed sessions.
- The latest observation time is visible. After 15 minutes without a new
  observation, `Stale data` appears with a concrete recovery action.
- `Refresh` requests lightweight telemetry first and then retains the complete
  incremental refresh with duration and changed-record reporting.

### Contract and privacy

`GET /api/usage` is read-only, persists nothing, and returns no paths,
transcripts, or message content. The percentage is the latest observation
emitted locally by Codex; it is not presented as an authenticated account query
or a fixed token-equivalent allowance.

The [official Codex documentation](https://learn.chatgpt.com/docs/pricing)
states that current limits are available in the usage dashboard or through
`/status`, that similar tasks can consume different amounts depending on model,
context, reasoning, and tools, and that additional weekly limits may apply.

### Verification

- 24 Python tests passed, including latest-valid-event selection, missing
  source, API response, staleness, and path omission.
- 7 Angular tests passed with 4% available, 96% consumed, observation time,
  stale warning, and the two-stage refresh.
- Production Angular build completed within budget.
- `npm audit --audit-level=moderate`: 0 vulnerabilities.
- Impeccable detector over HTML, SCSS, and TypeScript: 0 findings.
- Docker 0.24 stack built with a healthy API and dashboard available at
  `http://127.0.0.1:4200`.
- Real-browser validation against the active local source showed 2% available
  and 98% consumed from an observation under one minute old, without changing
  sessions or lifecycle decisions.

### Known limit

Codex does not expose an official account API here. When it emits no local
events, the latest value can age; the UI makes that explicit instead of
presenting it as current.
