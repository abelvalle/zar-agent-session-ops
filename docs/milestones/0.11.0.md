# 0.11.0 - Actualización en segundo plano / Background refresh

## Español

### Objetivo

Permitir que el dashboard actualice el inventario desde los archivos Codex sin
reiniciar la API ni mantener una petición abierta durante todo el escaneo.

### Implementación

- `POST /api/refresh` devuelve HTTP 202 e inicia el escaneo como tarea de fondo
  de FastAPI.
- `GET /api/refresh` informa `idle`, `running`, `completed` o `failed`, junto con
  inicio, fin y número de sesiones cuando corresponde.
- Un estado protegido por `threading.Lock` impide iniciar dos escaneos a la vez.
  El alcance es deliberadamente local al proceso porque Uvicorn se ejecuta con
  un solo worker.
- El escaneo reutiliza `scan_codex` y `sync_sessions`; no existe un segundo
  lector ni una ruta de escritura nueva sobre los JSONL.
- `serve --source` permite seleccionar explícitamente la fuente. Docker fija
  `ZAR_SESSION_SOURCE=/codex` y conserva el bind como solo lectura.
- El botón `Actualizar` lanza el trabajo, consulta el estado cada segundo y
  recarga salud, sesiones y bloqueos al completarse.
- La interfaz muestra progreso, resultado o error y cancela el sondeo cuando se
  destruye el componente.

### Seguridad y fallos

- La API sigue ligada a loopback. La operación POST solo sustituye metadatos
  Codex en SQLite; no mueve ni modifica sesiones originales.
- Los errores completos quedan en el log de la API. La respuesta pública usa un
  mensaje genérico para no revelar rutas locales.
- Un fallo conserva el último inventario válido porque `sync_sessions` solo se
  ejecuta después de terminar la lectura.
- Solicitudes recibidas mientras el estado es `running` devuelven el mismo
  trabajo y no crean otro.

### Verificación

- 12 pruebas Python aprobadas, incluida una actualización desde un JSONL
  sintético sin alterar la fuente.
- 3 pruebas Angular aprobadas, incluido el flujo `running -> completed` y la
  recarga del inventario.
- Sobre 461 sesiones reales, la primera solicitud respondió en 84 ms y una
  solicitud duplicada en 2 ms con el mismo `started_at`.
- La API respondió `ok` durante el escaneo y completó las 461 sesiones en unos
  15 segundos en ejecución nativa.
- Las imágenes API y dashboard 0.11.0 se construyeron correctamente.
- Un stack Docker aislado procesó una sesión Codex real, mantuvo `/codex` en
  solo lectura, ejecutó la API como UID 10001 y completó el refresco.
- El dashboard empaquetado mostró la confirmación de inventario actualizado y
  no generó errores ni avisos en la consola del navegador.

### Claude Code y OpenCode

Se comprobó Claude Code 2.1.128, pero el equipo no contiene transcripciones
JSONL en la ruta oficial `~/.claude/projects/<project>/<session-id>.jsonl`.
Los dos archivos de `~/.claude/sessions` son descriptores auxiliares de VS Code,
no conversaciones. El adaptador se pospone para no fijar un contrato con datos
que Anthropic no documenta como transcripciones. OpenCode tampoco dispone de una
fuente local real en este equipo.

La ubicación y retención de las transcripciones Claude Code se contrastaron con
la [documentación oficial de sesiones](https://code.claude.com/docs/en/sessions).
La ejecución posterior a la respuesta sigue el contrato oficial de
[tareas de fondo de FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/)
y el sondeo se cancela mediante
[`takeUntilDestroyed` de Angular](https://angular.dev/ecosystem/rxjs-interop/take-until-destroyed).

### Límites conocidos

- El estado vive en memoria y presupone un solo proceso Uvicorn. Se necesitaría
  coordinación persistente para varios workers o varias réplicas.
- El refresco es manual; no se añade un daemon ni un planificador nuevo.
- El sondeo usa un intervalo fijo de un segundo, suficiente para una herramienta
  local. WebSocket o SSE se justifican solo si aparecen más trabajos en vivo.

## English

### Goal

Let the dashboard update its inventory from Codex files without restarting the
API or keeping one request open for the whole scan.

### Implementation

- `POST /api/refresh` returns HTTP 202 and starts the scan as a FastAPI
  background task.
- `GET /api/refresh` reports `idle`, `running`, `completed`, or `failed`, plus
  start time, finish time, and session count when applicable.
- `threading.Lock` protects process-local state and prevents two simultaneous
  scans. This deliberately matches the single-worker Uvicorn deployment.
- The scan reuses `scan_codex` and `sync_sessions`; there is no second parser or
  new write path to JSONL sources.
- `serve --source` explicitly selects the source. Docker sets
  `ZAR_SESSION_SOURCE=/codex` and retains the read-only bind.
- The `Refresh` button starts the work, polls once per second, and reloads
  health, sessions, and blocked signals when it completes.
- The interface displays progress, result, or failure and stops polling when
  the component is destroyed.

### Security and failures

- The API remains loopback-bound. The POST operation replaces only Codex
  metadata in SQLite; it neither moves nor modifies source sessions.
- Full errors remain in API logs. The public response uses a generic message to
  avoid exposing local paths.
- A failure preserves the latest valid inventory because `sync_sessions` runs
  only after reading finishes.
- Requests received while state is `running` return the same job and do not
  create another.

### Verification

- 12 Python tests passed, including refresh from a synthetic JSONL without
  modifying the source.
- 3 Angular tests passed, including the `running -> completed` flow and
  inventory reload.
- Against 461 real sessions, the first request returned in 84 ms and a duplicate
  in 2 ms with the same `started_at`.
- The API returned `ok` during the scan and completed all 461 sessions in about
  15 seconds under native execution.
- API and dashboard 0.11.0 images built successfully.
- An isolated Docker stack processed one real Codex session, kept `/codex`
  read-only, ran the API as UID 10001, and completed a refresh.
- The packaged dashboard displayed the refreshed-inventory confirmation with no
  browser console errors or warnings.

### Claude Code and OpenCode

Claude Code 2.1.128 was inspected, but this machine has no JSONL transcripts at
the official `~/.claude/projects/<project>/<session-id>.jsonl` location. The two
files under `~/.claude/sessions` are VS Code support descriptors, not
conversations. The adapter remains deferred rather than establishing a contract
around data Anthropic does not document as transcripts. OpenCode also has no
real local source on this machine.

Claude Code transcript location and retention were checked against the
[official session documentation](https://code.claude.com/docs/en/sessions).
Post-response execution follows FastAPI's official
[background-task contract](https://fastapi.tiangolo.com/tutorial/background-tasks/),
and polling is cancelled with Angular's
[`takeUntilDestroyed`](https://angular.dev/ecosystem/rxjs-interop/take-until-destroyed).

### Known limits

- State is in memory and assumes one Uvicorn process. Multiple workers or
  replicas would require persistent coordination.
- Refresh is manual; no new daemon or scheduler is introduced.
- Polling uses a fixed one-second interval, appropriate for a local tool. Add
  WebSocket or SSE only when more live jobs exist.
